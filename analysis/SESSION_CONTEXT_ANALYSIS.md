# OpenClaw 세션 컨텍스트/캐시 분석

## 1. 목적
이 문서는 Telegram 그룹 세션 `agent:main:telegram:group:-1003782726441`를 기준으로,
OpenClaw가 긴 대화 문맥을 어떻게 다루는지와 실제 입력 토큰/캐시 사용량이 어느 정도였는지를 정리한 문서입니다.

핵심 질문은 아래 두 가지입니다.
- 세션 누적 토큰이 `241k`라면, 매번 그 정도가 통째로 모델 입력으로 들어가는가?
- 실제로 캐시는 얼마나 먹고, 왜 어떤 호출은 캐시율이 낮은가?

## 2. 결론 요약
- `241k`는 세션의 누적 사용량에 가까운 값이지, 매번 그대로 모델에 넣는 고정 입력값은 아닙니다.
- 하지만 이 그룹 세션은 실제 최근 호출에서도 `180k~239k` 수준의 큰 입력이 자주 발생했습니다.
- 따라서 비용 우려는 현실적입니다.
- 캐시는 동작하고 있지만, `도구 호출 결과`, `새 사용자 메시지`, `세션 요약 시점 변화` 때문에 프롬프트의 뒤쪽이 자주 바뀌어 캐시율이 출렁입니다.
- 짧은 시간 안의 연속 내부 호출은 캐시율이 매우 높지만, 새 사용자 요청이나 새 tool 결과가 끼면 캐시율이 급격히 떨어집니다.
- 하루 뒤 다시 같은 세션에서 말하는 경우에는 서버 쪽 input cache를 기대하기 어렵습니다. 기본 캐시는 보통 메모리 기반 단기 캐시이기 때문입니다.

## 4. OpenClaw가 문맥을 관리하는 방식
### 4.1 전체 세션 원문을 무조건 그대로 넣는 구조는 아님
OpenClaw는 현재 턴 입력과 과거 세션 기록을 분리해서 다룹니다.

관련 코드:
- 현재 턴 prompt + sessionFile 조립: `/usr/lib/node_modules/openclaw/dist/reply-CFQ8lILc.js:27540`
- 세션 열기: `/usr/lib/node_modules/openclaw/dist/pi-embedded-A-pNScBs.js:75256`
- 세션 정리/제한/압축: `/usr/lib/node_modules/openclaw/dist/pi-embedded-A-pNScBs.js:75313`

의미:
- 현재 사용자의 질문은 별도로 prompt로 들어갑니다.
- 과거 대화는 `sessionFile`에서 불러오되,
- 그대로 다 쓰는 것이 아니라 정리와 제한을 거친 뒤 모델 호출용 문맥을 만듭니다.

### 4.2 긴 세션은 압축(compaction) 대상
관련 코드:
- compaction 관련 설정: `/usr/lib/node_modules/openclaw/dist/reply-CFQ8lILc.js:9316`
- compaction 실행: `/usr/lib/node_modules/openclaw/dist/pi-embedded-A-pNScBs.js:74995`
- compaction summary 처리 흔적: `/usr/lib/node_modules/openclaw/dist/pi-embedded-A-pNScBs.js:74360`

의미:
- 오래된 대화는 그대로 다 남겨두는 것이 아니라 요약본으로 바뀔 수 있습니다.
- 즉, 누적 세션 토큰과 실제 현재 입력 토큰은 같은 값이 아닐 수 있습니다.

## 5. 실제 최근 호출에서 확인한 입력 크기
가장 최근 usage가 붙은 assistant 응답:
- 위치: `agents/main/sessions/249a5bca-6ac9-4ed2-80f5-c8f477574307.jsonl:2038`
- 시각: `2026-03-18T02:49:22.928Z`
- `input`: `182,191`
- `cacheRead`: `58,880`
- `output`: `112`
- `totalTokens`: `241,183`

해석:
- 이 호출의 전체 프롬프트 규모는 대략 `241k` 수준입니다.
- 다만 그중 `58,880` 토큰은 캐시에서 재사용되었고,
- `182,191` 토큰은 새로 입력 처리되었습니다.

즉,
- `241k` 전체가 매번 모두 새 입력으로 과금되는 것은 아니지만,
- 실제 새 입력만 해도 `182k`라서 비용은 여전히 큽니다.

## 6. 캐시 숫자의 의미
예를 들어 아래와 같은 usage가 있었다면,
- `input: 182,191`
- `cacheRead: 58,880`

의미는 다음과 같습니다.
- `input`: 이번 호출에서 새로 계산된 입력 토큰
- `cacheRead`: 이번 호출에서 캐시에서 재사용된 입력 토큰

즉 전체 프롬프트는 대략 다음과 같습니다.
- `182,191 + 58,880 = 241,071`

따라서,
- 캐시된 부분은 재사용되었고,
- 나머지 `182k`는 새로 모델 입력으로 처리된 것입니다.

## 7. 하루 뒤에도 캐시가 유지되는가
실무적으로는 **기대하지 않는 편이 맞습니다**.

근거:
- OpenAI prompt cache는 기본적으로 `in_memory` 보관 정책을 씁니다.
- 보통 유휴 `5~10분`, 길어도 `최대 1시간` 수준으로 보는 것이 안전합니다.
- `24h` 캐시는 요청마다 명시적으로 `prompt_cache_retention: "24h"`를 넣어야 합니다.
- 현재 OpenClaw 설정/코드에서 이를 명시적으로 사용하는 흔적은 찾지 못했습니다.

따라서,
- 짧은 시간 안의 연속 호출은 캐시가 먹을 수 있지만,
- 하루 뒤 다시 같은 대화를 이어갈 때는 서버 쪽 input cache hit를 기대하기 어렵습니다.

## 8. 캐시 비용 절감 폭
현재 모델은 `gpt-5.3-codex`입니다.

가격 기준:

- 출력: `$14 / 1M tokens`

즉,

최근 호출 예시(`:2038`):
- 일반 입력 `182,191`
- 캐시 입력 `58,880`

비용:

- 합계: 약 `$0.3307`

만약 캐시가 전혀 없었다면 약 `$0.4235` 수준이므로,
- 이 한 번의 호출에서는 캐시가 약 `$0.0928` 절약한 셈입니다.

## 9. 왜 캐시율이 낮아지는가
### 9.1 이 세션은 tool-heavy 세션임
세션 역할 분포:
- `assistant`: `991`
- `toolResult`: `807`
- `user`: `233`

즉, 단순 대화 세션이 아니라
- 파일 읽기
- 명령 실행
- 편집 결과
같은 도구 출력이 매우 많이 끼어드는 세션입니다.

### 9.2 새 사용자 메시지와 tool 결과가 프롬프트 뒤쪽을 계속 바꾼다
캐시는 프롬프트 앞부분이 이전 호출과 많이 같을수록 유리합니다.
하지만 이 세션은 아래 요소 때문에 프롬프트가 자주 달라집니다.
- Telegram 메타데이터(`message_id`, `sender_id`, `group_subject` 등)
- 새 사용자 질문
- 새 tool 결과
- 세션 압축 시점 변화

결과적으로,
- 어떤 호출은 직전 호출과 거의 같아서 캐시율이 매우 높고,
- 어떤 호출은 새 정보가 붙으면서 캐시율이 매우 낮아집니다.

## 11. 최근 요청들을 같이 보면 보이는 패턴
- **새 콘텐츠 전달형 요청**
  - 예: AI 뉴스 브리핑 전달
  - 캐시율 매우 낮음
  - 이유: 매번 본문이 거의 새 텍스트이기 때문

- **읽고 검토하는 tool-heavy 요청**
  - 예: `BOARD_OPS.md 읽어봐`
  - 전체 기준으로는 캐시가 절반 정도 먹을 수 있음
  - 이유: 중간 내부 호출이 직전 프롬프트를 많이 재사용하기 때문

- **수정 실행형 요청**
  - 예: `응 수정해`
  - 일부 캐시는 먹지만, 최종 단계 캐시율은 중간 수준 또는 낮은 수준이 될 수 있음
  - 이유: edit/exec/toolResult가 프롬프트 꼬리를 크게 바꾸기 때문

## 12. 운영 관점에서의 해석
이 그룹 세션은 아래 이유로 비용 친화적이지 않습니다.
- 세션이 매우 큼
- 그룹 세션이라 메타데이터가 자주 바뀜
- tool 결과가 많이 끼어듦
- 새 콘텐츠를 장문으로 전달하는 일도 많음

즉,
- OpenClaw가 문맥 압축과 캐시를 쓰고는 있지만,
- 이 세션 자체가 큰 입력을 반복적으로 만들기 쉬운 구조입니다.

## 13. 실무 판단
이 세션에서 비용을 줄이려면 캐시 자체보다 세션 구조를 손보는 쪽이 더 효과적입니다.
예:
- 그룹 세션과 작업용 세션 분리
- tool-heavy 작업은 별도 세션으로 분리
- 너무 길어진 세션은 주기적으로 리셋 또는 강한 압축
- 브리핑 전달용 대화와 운영 작업용 대화를 분리

캐시는 보조 수단이고,
핵심은 **큰 세션을 계속 한 방에 끌고 가는 구조를 줄이는 것**입니다.
