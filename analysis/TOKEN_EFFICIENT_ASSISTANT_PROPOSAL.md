# TOKEN_EFFICIENT_ASSISTANT_PROPOSAL.md

## 목적

이 문서는 현재 `.openclaw` 구조가 토큰을 많이 쓰는 이유를 정리하고, 이를 빅스비 같은 생활형 비서 구조에 적용할 때 토큰 사용량을 크게 줄이기 위한 설계 제안을 담는다.

대상은 "계속 켜져 있고", "짧은 요청이 많고", "반복 업무가 많고", "대부분의 턴에서 긴 추론이 필요하지 않은" 개인 비서형 에이전트다.

핵심 목표는 다음 네 가지다.

- LLM 호출 횟수 자체를 줄인다.
- 호출하더라도 프롬프트 길이를 짧게 만든다.
- 고성능 모델은 정말 필요한 턴에만 쓴다.
- 로그/메모리/자동화 구조를 토큰 친화적으로 재설계한다.

## 1. 현재 구조가 토큰을 많이 쓰는 이유

현재 `.openclaw`는 "유연한 에이전트"에는 강하지만, "저비용 상시 비서"에는 불리한 구조를 갖고 있다.

### 1.1 모든 일을 에이전트 턴으로 푸는 경향

`cron/jobs.json`을 보면 단순 점검, 알림, 브리핑, 상태 확인도 대부분 에이전트 턴으로 실행한다.

문제:

- 단순 조건 검사도 프롬프트를 매번 구성해야 한다.
- 로그 파일/상태 파일/지침 문서를 다시 읽게 된다.
- 작은 작업도 LLM 1회 호출 비용이 든다.

예:

- "서비스 active 여부 확인"
- "최근 체결이 3시간 이상 없으면 알림"
- "로그 마지막 decision timestamp 확인"

이런 것은 LLM보다 스크립트/규칙 엔진이 훨씬 싸다.

### 1.2 문맥 로딩 규칙이 넓다

워크스페이스 지침상 세션 시작 때 여러 문서를 읽게 되어 있다.

- `SOUL.md`
- `USER.md`
- 최근 memory 파일
- 필요 시 다른 운영 문서

이 방식은 사람 같은 연속성에는 좋지만, 매턴 또는 매세션 비용이 커지기 쉽다.

### 1.3 로그와 상태를 자연어로 재해석한다

현재 구조에서는 로그를 읽고 "무슨 일이 있었는지 설명해줘" 형태로 에이전트에게 다시 묻는 패턴이 많다.

문제:

- 구조화 가능한 데이터를 비구조화 요약으로 바꾸는 비용이 큼
- 요약을 위해 원본 로그를 다시 읽게 됨
- 변동 없는 상태도 매번 다시 설명함

### 1.4 heartbeat/cron이 모두 LLM 친화적으로 설계되어 있다

즉 "스케줄링 + 라우팅 + 판단 + 문장 생성"이 한 덩어리다.

이 구조는 개발은 빠르지만, 생산 환경에서 아래 문제가 생긴다.

- 알림 하나에도 모델 호출
- 중복 판단에도 모델 호출
- 사용자 가치가 낮은 점검에도 모델 호출

### 1.5 장문 프롬프트 중심 운영

현재 잡 메시지들은 꽤 길고, 출력 형식 요구도 상세하다.

이 방식은 브리핑 품질에는 유리하지만, 일상형 비서에서는 대부분 과하다.

## 2. 빅스비형 비서에서 토큰을 아껴야 하는 이유

빅스비형 비서는 일반 챗봇보다 짧고 잦은 요청이 많다.

예:

- "오늘 일정 뭐야"
- "알람 꺼"
- "방금 온 문자 요약해"
- "집에 가는 데 얼마나 걸려"
- "뉴스 세 줄만"

이런 시스템은 긴 대화보다 아래 특성이 중요하다.

- 빠른 응답
- 상시 대기
- 반복 요청 처리
- 동일한 사용자 패턴의 재사용

즉 비용 최적화의 핵심은 "잘 대답하는 것"보다 먼저 "LLM이 개입하지 않아도 되는 일을 분리하는 것"이다.

## 3. 설계 원칙

### 원칙 1. LLM을 기본 엔진이 아니라 마지막 단계로 쓴다

가능한 흐름:

입력
-> 룰 기반 라우터
-> 도메인 처리기
-> 정말 필요할 때만 LLM

### 원칙 2. 상태 판단과 문장 생성을 분리한다

예:

- 상태 판단: Python/JS 코드
- 문장 생성: 짧은 템플릿 또는 필요 시 소형 모델

### 원칙 3. 메모리는 "항상 읽는 문서"가 아니라 "필요할 때 조회하는 키-값/요약 계층"으로 바꾼다

### 원칙 4. 주기 작업은 대부분 비-LLM 파이프라인으로 돌린다

### 원칙 5. 고급 모델은 브리핑, 예외 처리, 장문 생성에만 쓴다

## 4. 권장 아키텍처

### 4.1 3단계 처리 구조

권장 구조:

1. Fast path
2. Tool path
3. Reasoning path

#### Fast path

완전 무-LLM 처리 구간이다.

대상:

- 정해진 명령
- 짧은 FAQ
- on/off 제어
- 현재 상태 조회
- 단순 포맷 변환

예:

- "오늘 일정"
- "최근 알림 보여줘"
- "업비트 봇 살아있어?"
- "3시간 무체결이야?"

이런 요청은 코드가 직접 응답 JSON을 만들고, 템플릿 문자열만 채우면 된다.

#### Tool path

도구 호출은 필요하지만 추론은 거의 필요 없는 구간이다.

예:

- 캘린더 조회
- 메일 제목 목록
- 최근 메시지 리스트
- 주가 현재가 조회

여기서는 슬롯 추출만 작게 하고, 나머지는 API/스크립트가 해결한다.

#### Reasoning path

정말 LLM이 필요한 구간이다.

예:

- 여러 정보원을 종합한 요약
- 모호한 요청 해석
- 장문 브리핑
- 우선순위 판단
- 예외 대응

중요한 점:

전체 트래픽 중 이 구간 비율을 10~20% 수준으로 낮추는 것이 목표다.

## 5. 구체적인 토큰 절감 전략

### 5.1 Intent Router를 먼저 둔다

첫 단계에서 작은 분류기로 요청을 분기한다.

분류 예:

- `command`
- `query_structured`
- `query_summary`
- `chat`
- `automation_event`

구현 방법:

- 규칙 기반 매칭 우선
- 부족할 때만 소형 모델 분류기 사용

예:

- "오늘 일정" -> `query_structured`
- "요약해줘" -> `query_summary`
- "불 좀 꺼" -> `command`

이렇게 하면 고급 모델 호출을 상당수 제거할 수 있다.

### 5.2 Prompt를 모듈화하고 지연 로딩한다

현재처럼 큰 시스템 프롬프트와 여러 운영 문서를 항상 읽지 말고, 의도별로 필요한 조각만 붙인다.

예:

- 캘린더 요청: 사용자 이름/톤 + 캘린더 포맷 규칙만
- 홈 IoT 제어: 제어 가능한 디바이스 목록만
- 뉴스 요약: 요약 스타일 규칙만

권장 방식:

- `core persona`
- `tool-specific policy`
- `output schema`

이 세 조각만 동적으로 합친다.

### 5.3 메모리를 3계층으로 나눈다

현재 문서형 메모리 방식은 읽기 비용이 크다. 아래처럼 바꾸는 것이 낫다.

#### L1: Session cache

- 현재 대화에서만 필요한 짧은 상태
- 최근 5~10턴 요약

#### L2: Structured profile

- 사용자 이름
- 자주 쓰는 장소
- 선호 표현
- 자주 쓰는 앱

JSON/SQLite로 관리하고 토큰 없이 조회 가능하게 한다.

#### L3: Long-term narrative memory

- 장기 취향
- 중요한 사건
- 관계 정보

이 계층은 항상 로드하지 않고, 특정 의도에서만 검색한다.

핵심:

`SOUL.md`, `USER.md`, daily memory를 매번 통으로 읽는 방식은 비서형 제품에 비싸다.

### 5.4 "설명용 요약" 대신 "기계용 상태"를 저장한다

예를 들어 업비트 상태 점검이면, 매번 로그를 읽어 자연어로 해석하지 말고 주기적으로 아래를 갱신한다.

```json
{
  "service_active": true,
  "last_decision_at": "2026-03-18T01:23:00Z",
  "last_trade_at": "2026-03-18T00:55:00Z",
  "error_recent": false,
  "health": "ok"
}
```

그다음 응답은 템플릿으로 만든다.

예:

- 정상: "업비트 봇은 정상입니다."
- 이상: "최근 10분 내 decision 로그가 없어 점검이 필요합니다."

이 방식은 토큰 사용량을 매우 크게 줄인다.

### 5.5 주기 작업은 "판단"과 "문장화"를 분리한다

현재는 주기 작업 하나가 보통 다음을 전부 수행한다.

- 파일 읽기
- 상태 판단
- 중요도 판단
- 문장 생성
- 전달

권장 분리:

1. 스크립트가 상태 계산
2. 규칙 엔진이 발화 필요 여부 결정
3. 발화가 필요할 때만 템플릿 또는 소형 모델 사용
4. 정말 복잡할 때만 대형 모델 사용

### 5.6 동일 브리핑은 증분 방식으로 만든다

뉴스/리포트/요약형 작업은 전체를 매번 새로 생성하지 말고 차분만 생성한다.

예:

- 이전 브리핑 hash 저장
- 신규 기사만 추출
- 신규 기사만 1차 요약
- 최종 브리핑에 붙이기

효과:

- 긴 기사 묶음을 매번 전량 프롬프트로 보내지 않아도 됨

### 5.7 출력 형식은 자연어 자유형보다 스키마 우선

가능하면 먼저 구조화 출력으로 받는다.

예:

```json
{
  "intent": "calendar_summary",
  "tone": "brief",
  "items": [
    {"time": "10:00", "title": "병원"},
    {"time": "14:00", "title": "회의"}
  ]
}
```

그 후 클라이언트나 템플릿 레이어가 이를 음성/텍스트로 변환한다.

이 방식은 같은 정보를 여러 스타일로 재사용할 수 있어 중복 호출을 줄인다.

### 5.8 TTS 전 단계에서 "음성용 압축 응답"을 만든다

빅스비형 비서는 음성 출력이 많다. 음성 응답은 장문일수록 사용자 경험도 나쁘고 토큰도 비싸다.

권장:

- 기본 응답 1~2문장
- 세부정보는 후속 질문 시만 확장

예:

- 기본: "오늘 일정은 두 개입니다. 오전 10시 병원, 오후 2시 회의입니다."
- 확장: "더 자세히 말해줘"일 때만 설명

### 5.9 모델 계층화를 강제한다

권장 모델 정책:

- 규칙/템플릿: 0 토큰
- 초소형 분류 모델: intent 분기
- 소형 모델: 짧은 요약, 슬롯 추출
- 대형 모델: 복합 요약, 애매한 요청, 계획형 응답

중요한 점:

기본값을 대형 모델로 두면 비용은 절대 안 내려간다.

### 5.10 silent success를 기본값으로 둔다

많은 자동화는 "문제가 없으면 아무 말 안 함"이 맞다.

예:

- 서비스 정상
- 신규 이벤트 없음
- 메일 긴급도 낮음
- 캘린더 변경 없음

비용 절감 효과:

- 쓸모없는 발화 감소
- 후속 대화 감소
- 불필요한 LLM 호출 감소

## 6. 빅스비형 비서에 맞는 권장 실행 모델

### 6.1 이벤트 중심 구조

권장 입력 소스:

- 사용자 직접 호출
- 시스템 이벤트
- 앱 푸시 이벤트
- 예약 작업

각 이벤트는 먼저 규칙 엔진을 통과한다.

예:

- "신규 메시지 1건" -> 규칙 엔진에서 중요도 낮음 -> 저장만, 무발화
- "30분 후 일정 있음" -> 템플릿 알림
- "사용자가 뉴스 요약 요청" -> 그때만 LLM

### 6.2 비서용 도메인 별 마이크로 핸들러

도메인을 나눈다.

- calendar handler
- message handler
- alarm handler
- device handler
- commute handler
- finance handler
- summary handler

각 핸들러는 가능하면 자체적으로 결과를 낸다.

LLM은 handler가 모호함을 만났을 때만 호출한다.

### 6.3 배경 요약 파이프라인

무거운 요약은 사용자 요청 시 실시간 계산하지 말고 배경에서 미리 압축해 둔다.

예:

- 메일 inbox digest
- 오늘 일정 digest
- 뉴스 top digest
- 가족/업무 메시지 digest

저장 형식:

```json
{
  "updated_at": "...",
  "summary_short": "...",
  "summary_medium": "...",
  "highlights": ["...", "..."]
}
```

사용자가 물으면 이 저장값을 바로 읽고, 정말 필요할 때만 재요약한다.

## 7. 현재 `.openclaw` 기준 리팩터링 제안

### 7.1 cron 잡을 세 종류로 분리

현재는 대부분 "LLM 잡"이다. 아래처럼 나누는 것이 좋다.

#### A. pure script jobs

LLM 없이 상태 계산만 하는 잡

예:

- 서비스 생존 여부
- 최근 로그 timestamp 계산
- 거래 통계 집계
- 뉴스 source 검증

#### B. template notification jobs

상태 계산 후 템플릿으로 즉시 알림하는 잡

예:

- "3시간 무체결"
- "401 인증 오류"
- "서비스 down"

#### C. LLM jobs

정말 해석/요약이 필요한 작업만 남긴다.

예:

- 일일 시장 브리핑
- 복합 뉴스 요약
- 장문 분석 리포트

### 7.2 heartbeat는 생활형 점검 전용으로 제한

heartbeat에는 아래만 넣는 것이 적합하다.

- 캘린더
- 메일 중요도
- 개인 메시지 중요도
- 장시간 무응답 상태에서의 조용한 체크

반대로 아래는 heartbeat에서 빼는 것이 낫다.

- 고빈도 상태 점검
- 분 단위 트레이딩 감시
- 정시 뉴스 발행

이건 cron/script가 맞다.

### 7.3 문서형 메모리 로딩을 기본값에서 제거

현재 문서 중심 메모리는 유지하더라도, 런타임 기본 경로는 아래로 바꿔야 한다.

- 기본: 구조화 프로필 조회
- 필요 시: 요약 메모 3~5줄
- 드물게: 원본 문서 조회

### 7.4 "최근 로그 N줄 읽고 해석" 패턴을 폐지

대신 각 도메인에 `status.json`을 두는 방식이 좋다.

예:

- `upbit-trader/runtime/health.json`
- `news/runtime/publish_status.json`
- `assistant/runtime/inbox_digest.json`

### 7.5 응답을 레벨별로 나눈다

같은 의도라도 길이를 기본적으로 분기한다.

- level 1: 1문장
- level 2: 3문장
- level 3: 자세한 설명

음성 비서의 기본값은 반드시 level 1 또는 level 2여야 한다.

## 8. 예상 효과

잘 적용하면 아래 개선을 기대할 수 있다.

### 토큰 비용

- 반복 점검류: 70~95% 절감 가능
- 알림류: 대부분 0토큰 또는 극소량 처리 가능

### 응답 속도

- 단순 요청: 훨씬 빨라짐
- 정형 응답: 거의 즉시 처리 가능

### 안정성

- 같은 입력에 같은 출력
- 포맷 통제 쉬움
- 중복 알림 제어 쉬움

### 운영성

- 실패 지점 분리 쉬움
- 로그 분석 쉬움
- 비용 추적 쉬움

## 10. 결론

이 구조를 빅스비 같은 비서에 그대로 가져가면, "모든 것을 에이전트가 읽고 해석하고 말하는" 방식 때문에 비용이 빠르게 커진다.

토큰을 줄이려면 본질적으로 다음 전환이 필요하다.

- 에이전트 중심 구조 -> 라우터 중심 구조
- 문서 읽기 중심 -> 구조화 상태 조회 중심
- 전부 LLM 호출 -> 일부만 LLM 호출
- 장문 응답 기본값 -> 짧은 템플릿 기본값

한 줄로 요약하면:

"비서는 항상 생각하는 존재"가 아니라, "대부분은 규칙과 상태로 처리하고 정말 애매할 때만 생각하는 존재"로 설계해야 토큰 비용이 내려간다.
